# 웹서비스 확장 로드맵 (초안, 2026-09-13)

## 결론 먼저

1. **지금 구조가 그대로 백엔드가 된다.** 데이터 플랫폼, 통계 엔진, 예측 모델, 도구 API, 에이전트의 층 구조는 웹서비스에서도 동일하다. 20주 계획을 바꿀 필요는 없고, 아래 "경계 5가지"만 지금부터 지키면 프론트를 얹는 비용이 작다.
2. **진짜 병목은 코드가 아니라 데이터 사용 권리다.** 개인 연구와 공개 서비스는 허용 범위가 다르다. 공개 서비스에는 라이선스 또는 제휴로 권리가 확보된 데이터만 노출한다. 이 조건이 안 되면 KBO 는 비공개로 두고 MLB 공개 데이터 버전을 먼저 공개한다.
3. **LLM 은 서비스의 한 기능이다.** 선수 예측표, FA 시장 보드, 보상선수 시뮬레이터는 LLM 없이도 페이지가 된다. 채팅은 프론티어 API + 도구로 먼저 열고, 파인튜닝 모델은 비용과 품질이 맞을 때 셀프호스팅으로 붙인다.
4. **차별화는 기록이 아니라 예측·설명이다.** 기록 조회는 야구나라, STATIZ 가 이미 잘한다. sabior 의 가치는 예측 구간, FA 금액·행선지 확률, 보상선수 후보, 그리고 근거를 설명하는 에이전트다.

## 지금부터 지킬 경계 5가지 (20주 계획에 반영)

| 경계 | 내용 | 계획 변경 |
|---|---|---|
| 도구 = HTTP API | 도구 레이어를 FastAPI 엔드포인트로 구현하고 에이전트도 같은 API 를 호출한다 | P3 W9. 원래 in-process 였던 것을 API 로. 1~2일 추가 |
| 예측은 배치 산출물 | 예측·FA 추정·팀 시뮬 결과를 야간 배치로 테이블에 저장(as_of 포함). 프론트와 에이전트는 읽기만 | P2 에 `projections`, `fa_estimates`, `team_sim_results` 테이블 추가 |
| 에이전트 무상태 | 세션과 도구 로그는 DB 에. 도구 로그가 곧 "근거 보기" UI 의 데이터 | P3 설계에 이미 포함 |
| 소스 어댑터 분리 | `etl/<source>/` 별로 수집기를 두고 스키마는 동일. 연구용 데이터를 라이선스 데이터로 교체 가능 | 사실 테이블에 `source` 컬럼 추가 (W3 스키마 v1.1) |
| 상용 가능 라이선스만 | 모델·라이브러리·데이터 모두 Apache 2.0 / MIT 급 | 베이스 모델 후보에서 EXAONE 3.5 제외 (docs/base_model_candidates.md) |

## 기술 스택 제안 (1인 운영 기준)

| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트 | Next.js + Tailwind + shadcn/ui, 차트는 Recharts | 배포 Vercel 무료 티어. 서버 컴포넌트로 예측표 SSR |
| 백엔드 | FastAPI (이미 계획) | Fly.io 또는 Railway, 월 $5~20 |
| 데이터 | DuckDB 파일(배치 산출물, 읽기 전용) + Postgres(Supabase 무료 티어, 계정·로그) | 쓰기 트래픽이 생길 때만 Postgres |
| LLM | 채팅: Claude API + 도구 호출. 셀프호스팅: vLLM + LoRA 어댑터를 RunPod/Modal 서버리스 GPU 에 | API 는 질문당 수 원~수십 원. GPU 는 가동 시간당 약 $0.5~1 |
| 배치 | GitHub Actions cron 또는 서버 cron. 야간 1회 | 실패 알림은 Slack/메일 1개 |
| 관측 | 도구 로그 테이블 + 간단 대시보드 | 이미 P3 설계 |

## 리스크

- **권리 미확보 공개.** 서비스 중단과 분쟁 리스크. 데이터 권리 없이는 공개하지 않는다는 규칙을 ADR 로 고정한다.
- **1인 운영.** 배치 실패, 시즌 중 데이터 갱신, 모델 드리프트. 알림은 최소, 수동 복구 절차를 문서화.
- **차별화 부족.** 기록 조회로 경쟁하면 진다. 예측 정확도(백테스트 공개)와 설명 품질로 승부.
- **LLM 비용 폭주.** 질문당 도구 호출 수 제한, 캐시, 로그인 없는 사용자에게는 일일 한도.
